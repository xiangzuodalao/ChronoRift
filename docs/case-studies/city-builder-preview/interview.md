# City Builder：求职与面试讲述

适合用来介绍 Agent Harness、运行时工具集成与验收设计能力。源码身份、原始候选和逐项结果以本目录的案例记录为准。

## 简历要点

> 将基于 Pi SDK 的 ChronoRift 应用于此前未用于工具接口设计的第三方 Godot 项目 Kenney City Builder；由真实 Agent 使用现有工具自主调查并修复建筑预览重复重建，产品源码、工具与协议零修改，候选首轮通过全部 66 项独立验收。

> 设计相同模型、任务和预算下的 coding-only 对照，以会话外检查器在 SRT 只读运行副本中驱动真实输入；两组首轮候选一致且均通过 66/66 项检查，空闲 120 个 process 完成周期内预览添加和移除均由 120 次降至 0，保留初始化、15 种模型双向切换与回绕等行为。

这两条分别讲工具复用和验证设计。如果简历只能放一条，优先第一条。不要用“零项目专属代码”概括整个案例：产品和 Agent 工具没有项目适配代码，案例运行脚本与独立检查器包含固定项目配置和验收知识。两组都通过，不据此声称修复率优势。

## 三分钟讲稿

我选择此前未用于 ChronoRift 接口设计的 Kenney City Builder，检验现有工具能否支持外部项目。任务是消除选中建筑不变时的重复预览重建，同时保留首次显示和切换更新。

我负责运行环境、工具接入和验收，真实 Pi Agent 自己决定读代码、调用工具、修改和验证的顺序。ChronoRift 提供私有候选工作区和现有 coding、游戏工具。产品源码、工具和协议没有修改；项目专属知识只出现在案例配置和会话外检查器中。

我固定上游提交，先运行 coding-only，再运行 ChronoRift。两组使用独立的新会话、相同任务和模型，每组 600 秒、所有工具合计最多 256 次调用。coding-only 去掉游戏工具及对应说明，Agent 看不到另一组结果和独立检查器。

两组通过源码定位，写出了完全相同的 patch。coding-only 做了静态检查，没有运行 Godot。ChronoRift 组先修改，再查询候选初始状态，随后自主补充第二次运行：相隔 1120 个 process frame 的两次查询返回同一预览对象句柄，选中项查询也均为零。它取得了候选的运行时身份采样，但没有运行原版复现问题，不能讲成运行时定位根因。

独立检查器在沙箱的只读运行副本里加载真实主场景，用输入 action 驱动切换，记录预览节点的添加、移除、身份和模型来源。原版在空闲 120 个实际 process 完成周期内发生了 120 次添加和 120 次移除；两个首轮候选都是零。检查还覆盖初始化、15 种模型双向切换与回绕、同帧相反输入和旋转，两组都通过全部 66 项，不需要后续修复。

这次对照没有显示候选质量差异，我不会据此声称修复率优势。它展示了现有工具在一个外部项目上的复用，以及自主调查、实际执行和独立验收之间的分工。完整重建计数和输入驱动属于验收代码，Agent 的 query 只提供当时的状态。CPU、FPS 和跨项目成功率仍需要另外测量。

## 面试追问

**“你说没有项目适配，具体指什么？”**

ChronoRift 的产品源码、工具定义、协议和运行时观察面没有为 City Builder 添加分支。案例运行脚本复用现有 Preview 的依赖入口，配置固定源码、任务、预算和两组工具条件。项目节点路径、模型列表和输入 action 出现在会话外的独立验收代码中，需要明确披露这部分人工工作。

**“修复是你写的，还是 Agent 写的？”**

两个候选 patch 都来自真实 Pi 会话，逐字节相同，均在首轮通过独立验收，没有后续修复。我的贡献是提供工具和执行环境，设计共同任务、运行配置与独立验收，并整理可审阅证据。

**“运行时工具帮助 Agent 找到了根因吗？”**

这次 Agent 从源码定位问题并修改后，进行了两次候选运行，共调用 2 次 launch、6 次 query、2 次 stop。第二次运行中，对容器子节点的查询在 process frame 657 和 1777 都返回 `object.3`，对选中项的查询在 658 和 1778 都返回零。它补充了候选运行时身份采样，但没有运行原版复现问题，因此不能描述为运行时定位根因。完整的预览添加和移除计数来自会话外的独立检查器。

**“模型总结和工具结果不一致时怎么办？”**

以工具返回的实际执行记录为准，并保留差异。这个案例中，ChronoRift 组的总结把 Godot 退出码写成了零；实际两次运行都由 stop 终止，Godot 子进程字段为 `run.signal=SIGTERM`、`run.exitCode=null`；顶层 wrapper 和导入进程的退出码为零，需要区分进程层级。停止运行是正常清理路径，但不能因此改写进程的退出事实。两组出现的工具失败也保留，不能只展示最后一次成功返回。

**“为什么不用模型自己的测试作为最终结论？”**

Agent 选择的验证可能只覆盖它当前想到的路径。这个任务除了空闲状态，还必须保留初始化、双向切换、首尾循环，以及同帧相反输入最终抵消时不重建。固定检查器对原版和每个候选应用同样的输入与判定，使这些遗漏可见。检查器自身也需要用原始缺陷和故意破坏初始化、切换行为的候选验证。

**“66 项通过意味着什么？”**

它表示候选在这些具体运行场景中满足了预览生命周期、模型来源、偏移和输入行为的判定。这 66 项包含两个方向的完整遍历及切换后的空闲检查，彼此有关联，不是 66 次独立实验。它不覆盖像素画面、完整玩法或性能指标。

**“为什么要区分 process frame、physics tick 和时间？”**

预览更新发生在 `_process`，所以空闲窗口按观察到的 process 完成周期计数。Godot 的 `process_frame` 信号在节点执行 `_process` 前触发，检查器要在 Builder 执行后再采样。physics tick 和 Host 时间另行记录，不能用“等了一段时间”替代已经执行了多少次预览更新。

**“两组都通过，还有什么价值？”**

两组首轮都通过 66/66，且候选逐字节相同，说明这次修复可以用 coding-only 工具条件完成。案例展示的是现有工具在外部项目上的复用、Agent 实际取得的运行时采样，以及隔离执行和独立验收如何工作。耗时、调用数量或 token 的一次差异可以描述，但不能据此宣布工具总体更高效或修复率更高。

**“运行环境如何隔离？”**

coding 操作使用私有候选工作区；Godot 使用独立 staged copy，运行时游戏源码只读并检查完整性。原生导入可以使用单独的可写一次性副本，之后检查导入结果再构建运行副本。沙箱启动失败会报告前置条件失败，Host 凭据不进入工具环境，项目内容也不能改变 Host 权限。

## 展示顺序

面试时先展示共同任务和两组结果，再打开原始候选 patch、Agent 的实际调用摘录，以及独立验收的空闲窗口记录。用一条完整路径说明“任务如何进入 Agent、工具实际返回什么、候选如何被复查”，其余实现细节留给追问。

保留两组首轮原始结果及工具失败；运行完成只表示 Agent Loop 结束。简历和口述只引用案例记录中已经出现的结果，不补写未发生的调查步骤，也不把检查器的观察归给 Agent。
